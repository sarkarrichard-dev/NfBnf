<objective>
Tracer slice for Phase 2, crypto first (D-02): prove end to end — recorded real Delta
traffic, replayed through the real DeltaClient with an injected fault, through the
executor and the lane, to the journal and Telegram — that a live crypto entry whose
outcome is unclear is settled from Delta's own order list, never re-sent and never left
untracked.

The concrete "cancel issued while an order is being placed" case on Delta (research
Critical Finding 2 — no cancel exists today): the lane sends a market order, Delta's reply
is lost, and today crypto/lanes.py:818-827 records "order failed — we are flat" even though
the order may be live on Delta with its bracket stop. This plan replaces that guess with a
lookup by our own client_order_id (D-06), cancels the order if it is somehow still working,
and records exactly what filled. If Delta cannot be asked either, the order is treated as
not placed and the slot is held so no second order goes out (D-07).

Design note (assumption-delta, recorded as a decision): each fix in this phase is built
once per broker as two symmetric implementations sharing one test helper
(tests/_fake_brokers.py). Delta's settle-by-client_order_id here is the mirror of Dhan's
settle-by-correlationId in plan 02-03; Delta's lock is _STATE_LOCK because that is what its
placement holds, Dhan's is execution_safety.acquire_execution_lock for the same reason.

D-05 (sequencing): this plan and 02-03/02-04 carry the two higher-risk fixes (ORD-01
cancel races, ORD-02 disconnect reconciliation) and run in Waves 1-4; 02-06/02-07's
lower-risk ORD-03/ORD-04 (websocket reconnect, tick-feed fallback) run after, in Waves
5-6 — the urgent-two-before-the-other-two order CONTEXT.md D-05 locked in, applied within
each broker.

Purpose: crypto aims at real money around November 2026, so its order path is hardened
first. Output: the D-03 capture tool and first recorded Delta traffic, the shared replay
helper, DeltaClient cancel/lookup methods, executor settlement, lane wiring, tests.
